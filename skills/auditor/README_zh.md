# Auditor（一致性校验）

Auditor 对初始计划、变更日志和实际代码进行独立的一致性校验。它以对抗性审计员身份运行，对编码过程零先验知识——变更日志是它唯一的意图来源。

## 何时使用

- 合并代码前，验证实现是否与记录的意图一致
- `/code-modification` 和 `/log-change` 完成后
- 存在来自 `/deep-plan` 的任务包时，可执行三方校验

## 工作流

### Phase 1: 输入收集

1. **变更日志**（必填）：读取用户指定的日志文件。
2. **任务包**（可选）：如果提供，读取 `.claude/temp_task/{task_packet_file}`，从 `sender_payload.plan` 提取初始计划。
3. **源代码**：读取变更日志中引用的全部文件。

### Phase 2: 校验

跨 8 个维度校验代码与日志的一致性：

| 维度 | 检查内容 |
| :--- | :--- |
| 数据流 | 流向与描述一致；无隐藏副作用 |
| 数据结构 | 定义是否合理；有无风险类型转换 |
| 框架完整性 | 装饰器/中间件状态；有无全局状态污染 |
| API 一致性 | 签名与文档匹配；参数类型严格 |
| 流水线影响 | 是否破坏已有功能 |
| 涟漪效应 | 修改函数的 1 级 import/usage 检查 |
| 性能与安全 | OOM 风险、算法复杂度 |
| 测试策略 | 关键路径覆盖；拒绝仅 mock 测试 |

### Phase 3: 输出

生成两张表：

- **Table 1: 意图与实现对照** — 三角校验初始计划、变更日志和实际代码。报告差异。
- **Table 2: 防御性审计** — 检查副作用、涟漪效应、测试策略和性能安全。

### Phase 4: 停止

审计员停止并给出选项：修复 / 接受 / 继续调查。

## 校验模式

| 模式 | 条件 | 行为 |
| :--- | :--- | :--- |
| 三方校验 | 提供了任务包 | 计划 vs. 日志 vs. 代码 |
| 两方校验 | 无任务包 | 仅日志 vs. 代码（计划列标记 N/A） |

## 禁止事项

- **只读**：审计员不可修改代码。
- **禁止假设**：无法读取文件时报告该情况，而非猜测。

# Receiving Feedback（代码审查处理）

Receiving Feedback 在实现前对代码审查评论进行技术验证。它执行"先验证、后实现"的工作流——反馈在任何修改之前必须对照代码库进行检查。

## 何时使用

- 收到代码审查反馈时（来自团队成员、外部审查者或 PR 评论）
- 审查评论不明确或技术上存疑时
- 多个审查项需要按优先级处理时

## 工作流

### Phase 1: 阅读和理解

阅读全部反馈项，不做反应。用自己的话复述每条需求，不清楚时请求澄清。

### Phase 2: 验证

对照代码库检查每条建议：

- 对当前项目是否技术上正确？
- 是否破坏已有功能？
- 当前实现是否有存在理由？
- 是否与先前的架构决策冲突？

### Phase 3: 评估和响应

- 正确：客观确认，进入实现。
- 不正确或有风险：以技术论据反驳。
- 不清楚：在实现任何内容之前停止并请求澄清。

### Phase 4: 实现

逐项进行，按优先级排序：
1. 阻塞性问题（破坏性 Bug、安全问题）
2. 简单修复（拼写、导入）
3. 复杂修复（重构、逻辑）

每次修复后单独测试。

## 处理不明确的反馈

如果任何一项不清楚，全部停止。不要在等待澄清的同时实现已理解的项——各项之间可能存在依赖关系。

## 何时反驳

- 建议破坏已有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（功能未被使用）
- 对当前技术栈不适用
- 与先前架构决策冲突

## 禁止事项

- 禁止表演性认同（"说得对！"、"观点正确！"）
- 禁止感谢表达（"感谢指出！"）
- 禁止未验证即盲目实现

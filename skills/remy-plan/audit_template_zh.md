# 计划深度分析表格模板

你必须按以下顺序输出 5 张 Markdown 表格。**每张表格前后各空 1 行。**

### 🧩 表 1: 歧义消除矩阵

*   **目标**: 明确用户意图、契约、范围和验收。实施自由度须有明确边界，不得遗留需要用户决定的事项。
*   **强制规则**: 超时、重试、库选择若影响承诺行为仍须确定；否则写明可变范围、约束和重新询问条件，不以二级分级控制推荐。

| 决策点 | 选项 | 已定约束 / 实施边界 | 理由与来源 |
| :--- | :--- | :--- | :--- |
| *示例: 超时* | *默认 / 30秒 / 60秒* | *采用已约定契约要求的超时* | *引用要求及受影响的失败行为* |
| *示例: 内部存储* | *现有兼容表示* | *可在已约定的所有权与接口约束内选择实现* | *写明边界及需要新增用户决定的条件* |

### 🧪 表 2: PBT 属性规约

*   **目标**: 仅在任务契约支持时定义性质，写明输入范围和前提，不提出无依据的全输入主张。
*   **类别**: 幂等性、往返性质、不变量保持、交换律。保留性质表；没有适用性质时显示 N/A 及理由，JSON 使用 `pbt_specs: []`。一般场景、兼容与恢复检查放入表 5。

| 功能模块 | PBT 属性类型 | 不变量描述 | 证伪策略 |
| :--- | :--- | :--- | :--- |
| *示例: 解析器* | *可逆性* | `decode(encode(x)) == x` | *随机 Unicode 字符串* |
| *示例: 钱包* | *守恒性* | `balance >= 0` 恒成立 | *并发扣减* |

### ⚖️ 表 3: 逻辑与契约审计

*   **数据流**: 验证上下游参数兼容性。
*   **系统风险**: 检查全局状态修改或操作系统特定假设。

| 维度 | 检查项 | 状态 | 决策/规约 |
| :--- | :--- | :--- | :--- |
| **数据流** | 上游依赖 / 下游兼容 | Pass/Warn | （必须定义具体数据契约） |
| **数据流** | 新增可变状态实体（schema 列 / 配置项 / sentinel 文件）是否同时列出 init / read / write 三路径 | Pass/Warn | Write 路径缺失时必须在表 1 显式声明该实体为 init-once read-only |
| **一致性** | 函数签名 / 库调用 | Pass/Fail | （递归对照定义检查） |
| **数据结构** | 常量 / 参数 / 配置 | Pass/Locked | 复用适用机制；新增配置须有实际可变性需求，不统一要求参数化 |
| **系统风险** | 副作用 / 环境兼容 | Pass/Warn | （检查全局机制与操作系统差异） |
| **复杂度** | 时间 / 空间 / OOM | Pass/Warn | （评估循环与内存使用） |
| **并发与锁** | 读写冲突 / 死锁 | Pass/Warn | （检查文件 IO 与共享资源） |
| **交接决定完备性** | 用户决定已明确 / 实施边界已写明 | Locked | 与表 1 一致；JSON 保留原维度枚举值，不恢复所有技术细节必须固定的要求 |

### 🛠️ 表 4: 物理变更预演

*   **修改位置与任务属性**: 保留原 `scope_position` 字符串，说明实际位置、职责、契约要求和受影响消费者；可按需使用 `{字段：值｜字段：值}`，不形成新等级。参见 SKILL.md Phase 3 的 Task Attribute Reference。
*   **涟漪效应**: 确认导入与依赖不产生循环引用。

| 文件路径 | 定位 | 操作 | 简述 | 修改层级 | 涟漪效应 |
| :--- | :--- | :--- | :--- | :--- | :--- |

### ✅ 表 5: 验证计划

*   **目标**: 定义实现完成后的端到端验证方法。
*   **覆盖**: 将每项目标、保持契约及选定方案的适用分支关联到具有方法和可观察预期的检查；再反向核对每项检查的要求、依据、适用条件及相关表 4 变更，包括受影响但未修改的消费者。复用批准或跳过确认不免除验收义务。
*   **适用性**: 一个检查可以覆盖多个义务，但条件和各项结果须可区分。不强制验证未采用的候选，也不要求支持约定契约之外的版本／数据组合；仍须验证契约要求的拒绝或隔离行为。N/A 只表示真正不适用并须说明理由，未知或尚未执行不等于 N/A；影响验收成立的未知仍是对应范围的阻塞，不是非阻塞假设。计划检查不是已通过结果。
*   **交接**: 将覆盖关系和具体检查内容保留在 Phase 6 的原文本字段中。已定内容的漏映射直接补齐；新事实或决定沿既有路由与预算处理，不新增确认循环。

| 验证步骤 | 方法 | 预期结果 | 回退条件 |
| :--- | :--- | :--- | :--- |
| *示例: 单元测试* | `pytest tests/test_auth.py -v` | 全部测试通过 | 回退该 commit |
| *示例: 集成测试* | 在选定场景适用的成功与失败条件下调用端点 | 响应及保持行为符合已定契约；仅在适用时加入表 2 性质 | 停止受影响的切换，在已批准恢复边界内排查 |
| *示例: 回归测试* | 运行全部测试集 | 无新增失败 | 排查后再决定是否继续 |

> **⚠ 检查点**: 保留 5 张表；真正不适用的项显示 N/A 及理由，JSON 字段不变。仅在授权、模式允许且没有阻塞时，进入 **Phase 6 (Evidence Packet Generation)** 执行原五步。原生 Plan 只写指定计划文件；其他情况下说明未产包原因，不更新活动指针、不提供执行命令。随后遵循固定 Phase 7 停止流程。

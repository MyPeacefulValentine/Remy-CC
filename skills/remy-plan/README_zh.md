# remy-plan（架构预审）

remy-plan 是一个零代码架构审计协议。它要求 AI 在编写任何实现代码之前，完成歧义消除、不变量定义和逻辑推演。核心原则：**先决策，后编码。**

## 何时使用

- 修改核心逻辑或共享组件的复杂重构
- 需求不明确或存在多条实现路径的新功能开发
- 数据迁移、权限变更或不可逆操作等高风险场景

## 工作流

### Phase 1: 上下文加载

AI 首先检查 `.claude/logic_index.db` 是否存在：

- **存在**：对目标文件运行 `impact.py`，生成双向影响报告——上游（谁调用了此代码）和下游（此代码调用了谁），包含跨层警告。按当前决策需要读取相关定义和行区间，不要求固定深度的全部文件。跨层影响标记后进入 Table 3 审计。
- **不存在**：提示用户运行 `/remy-index`，或回退到基于 grep/glob 的手动探索。

两条路径均核对影响提案的定义，说明尚未解决的假设和范围，不宣称所有依赖已知。

还会执行**复用扫描**：对任何计划新建的函数或工具，搜索项目中是否已存在类似实现。若存在可复用函数，计划必须引用已有实现而非提议新代码。

### Phase 2: 需求复述确认闸门

保留可见检查点。请求或适用批准中的目标、可验证验收和边界完整时，才可输出 `Restatement skipped: spec-complete` 并说明跳过依据；错误日志本身不足以确定预期。否则将**目标 / 已表达的动机 / 范围外**嵌入二选项 `AskUserQuestion`；不推测动机。用户指出偏差后合入修正，复述循环直至确认。

### Phase 3: 交互式歧义消除（循环）

保留强制五类清单：接口契约、资源依赖、行为边界、执行顺序、变更边界，逐项交代或说明 N/A。需要用户决定的备选方案包含推荐及依据，依赖问题仍按顺序呈现。推荐以目标、硬约束、责任和实际决定依赖为依据，不由实现级/架构级或最小差异默认值控制。可用 `{修改边界：模块内｜契约要求：保持}` 在原文本字段中按需说明任务属性。

收到回答后仍搜索相关代码并执行**交叉约束验证**；冲突重新呈现，不因新选择而自动否定原硬要求。用户所属决定须明确，不改变已定行为的实施细节可保留写明边界的自由度。

### Phase 4.1: 假设清单与场景探测

循环退出后，事实假设使用共享 `[✓]` / `[~]` / `[?]` / `[×]` 证据状态，需要时附加已有依据，如 `[~｜源码]`。用户选择使用 `[用户决定]`，不混入证据状态。`[事实问题]` 可按需附加当前的只读查证或实验验证方式；表格已有方法列时不重复。技术问题先查只读证据，临时探测须获授权，原生 Plan 不执行探测。

问题按依赖及对提案的影响分批呈现，不按置信度排序。无法执行或没有结论的观察保留证据缺口；用户选择不能核实技术断言。反证或否决使相关前提和决策回到 Phase 3。一次性保护只限制重新生成完整清单，不跳过遗留项复核；阻塞须被解决，或通过明确的范围决定消除依赖后，计划才可继续。

### Phase 4.2: 场景确认闸门

按实际契约、责任、交互或异常行为变化触发；只有不存在这类变化或已有批准覆盖完整组合行为时才可说明依据后跳过。只确认未被批准覆盖的新增或变化部分。两部分都需要确认时，AI 以单次 `AskUserQuestion` 呈现两个问题；整部分已有批准则注明依据，作为剩余问题的上下文而不重问。两部分仍分别核对——主成功场景（用例法：前置条件 → 触发动作 → 主流程编号步骤 → 后置结果）与扩展/异常场景（逐条 `异常条件 → 预期行为`）各承载于问题描述中，均附确认/有偏差二选项。措辞级偏差自由循环修正；决策级偏差经独立计数器 `_scenario_pass` 至多一次回退到 Phase 3 循环。

### Phase 4.3: 计划-代码对齐检查

生成表格前逐目标交代新鲜度：核对代码相关定义、文档段落或新建项的现有集成点。可复用明确且仍适用的新鲜观察，否则重新读取必要内容；有矛盾则返回决定循环，不能只选择部分目标交代。

其后 Phase 4.4（Schema 删除全树扫描）与 Phase 4.5（孤儿创建检测）继续把关，防止死代码与漏改的删除影响。

### Phase 5: 五表审计

Phase 4 全部通过后，AI 按 已加载的`language.md`指令 加载语言匹配的模板（`audit_template_zh.md` 或 `audit_template_en.md`），生成五张表：

| 表格 | 用途 |
| :--- | :--- |
| 歧义消除矩阵 | 明确用户决定及实施自由度边界；遗留用户所属决定阻塞交接。 |
| PBT 属性规约 | 记录有依据且写明输入域和前提的性质；无适用项时显示 N/A、数组为空。普通行为检查放验证表。 |
| 逻辑与契约审计 | 检查数据流一致性、复杂度（Big-O）、并发风险和系统副作用。 |
| 物理变更预演 | 列出每个待修改的文件、函数和操作类型，附带涟漪效应估算。 |
| 验证计划 | 将目标、保持契约和选定场景分支关联到可观察检查，并反向核对要求、适用条件及变更；包含失败处置。复用批准不免除覆盖。 |

### Phase 6: 任务包生成

五表生成后，仅在授权、模式允许且无阻塞时，AI 将 `AgentTaskPacketLite` JSON 文件写入 `.claude/temp_task/task_{TIMESTAMP}.json`。原 `analysis` 和 `plan[]` 文本字段保留验收方法、预期结果、适用条件及失败处置；必需验收缺口不得隐藏为非阻塞假设。包含：

- **证据链**：审计过程中读取的每个文件的原文摘录。
- **变更提案**：映射到证据引用的文件级操作。
- **Git 版本**：Commit Hash 和时间戳。

获准写包后保留 `.active_packet` 更新步骤，并核对任务关联；不删除标记绕过拒绝。原审计及留档 JSON 结构保持，策略和实施边界写入已有文本字段，不引入新校验器或契约扩展。原生 Plan 只写指定计划文件；没有实际任务包就不激活或提供执行命令。

### Phase 7: 强制停止

AI 停止并给出三个选项：

> 审计完成。[继续执行] / [修改计划] / [取消]？

此阶段不产生任何代码。

## 计划-修改-审计 流水线

remy-plan 是三 Skill 流水线的第一阶段：

```
/remy-plan
  └─→ 写入 .claude/temp_task/task_{TIMESTAMP}.json
         └─→ /remy-patch task_{TIMESTAMP}.json
               （以 proposed_changes[] 作为变更约束）
                      └─→ /remy-audit [日志文件] task_{TIMESTAMP}.json
                            （三方校验：计划 vs. 变更日志 vs. 代码）
```

没有证据包时，`/remy-patch` 仍遵守用户批准范围和原生权限，但不具有任务包专属检查；`/remy-audit` 使用两方校验。原生 Plan 是独立机制，不自动生成证据包；任务包存在也不是执行授权。

## 禁止事项

- **禁止生成代码**：此阶段严禁生成或修改任何实现代码。
- **禁止假设**：AI 不得假设用户意图，必须通过提问确认。

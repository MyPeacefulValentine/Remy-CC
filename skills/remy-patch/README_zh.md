# remy-patch（工程化代码修改）

remy-patch 通过依赖追踪、框架完整性检查和任务策略执行修改，核对相关定义而不把对话记忆当源码证据。上下游适配遵循选定契约；新增配置须有实际可变性；已批准的整体调整不再重复要求证明增量修改不可能。

## 何时使用

- `/remy-plan` 审批后，执行有边界约束的计划变更
- 修改、重构或优化现有代码
- 存在来自 `/remy-plan` 的任务包时（可选，复杂变更推荐使用）

## 工作流

### Phase 0: 任务包加载（条件执行）

如果提供了 `task_packet_file` 参数，Skill 读取 `.claude/temp_task/{task_packet_file}`，以 `proposed_changes[]` 作为权威变更范围。禁止超出该范围的修改。未提供任务包时，进入自由发现模式。

### Phase 1: 依赖发现

1. 检查 `.claude/logic_index.db` 是否存在。存在时对目标文件运行 `impact.py`，生成双向依赖报告（上游调用者和下游被调用者）。
2. 逻辑索引不可用时，回退到基于 grep/glob 的手动追踪。
3. 按实现需要读取相关定义和行区间，不要求固定深度的全部文件。
4. 验证待使用的外部函数签名。

### Phase 2: 框架合规检查

检查目标文件中是否存在对语言/特性有约束的编译器装饰器或元编程模式。若检测到，验证新代码与其兼容。未检测到时跳过。

### Phase 3: 执行

对每个待修改文件：

1. **预读取与缓存** — 读取文件并缓存原始内容，用于可能的回滚。
2. **发现检查点**（仅 packet 模式） — 每次 Edit 调用前检查 3 个条件：
   - H1: 文件不在 `proposed_changes[]` 中（范围溢出）
   - H2: 目标函数签名自审计以来已变化（计划过期）
   - H3: 编辑将违反 `sender_payload.analysis` 中的约束（约束冲突）

   条件触发时停止相关编辑：范围变化取得授权，过期事实重新核实，要求冲突先解决决定，不提供笼统忽略选项。保留原始内容与本次修改依据，获准恢复前检查并发变化，不能覆盖其他写者。
3. **编辑与验证** — 使用工具结果及适当差异/静态检查并记录修改后状态，不为证明工具成功而重复读取。
4. **行为决定日志**（仅 packet 模式） — 实际行为、资源、顺序、边界选择继续记录到 `.claude/temp_decisions/decisions_{PACKET_ID}.md` 并注明依据；新用户决定须事前解决，日志不授权，普通语法细节不强制记录。

### Phase 4: 验证

运行相关测试及原计划/分析字段携带的适用验收，包括已列明的手工、兼容与恢复检查；逐项说明已执行、失败或未执行及原因。普通失败在已批准范围内诊断修复并重验；扩大范围、效果未知、接受失败或未授权回滚时请求决定。

## 流水线集成

此 Skill 是 计划 → 修改 → 审计 流水线的第二阶段：

```
/remy-plan → 任务包 → /remy-patch → /remy-audit
```

任务包增加流程专属范围检查。没有任务包时仍遵守用户授权和原生权限；任务包存在不授权执行。

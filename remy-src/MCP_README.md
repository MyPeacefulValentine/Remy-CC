# remy-index MCP Server

A stdio-based [Model Context Protocol](https://modelcontextprotocol.io/) server that exposes code intelligence queries from the remy-index SQLite database. Since R4.1 the production host is the Rust binary — `remy-cc mcp` (rmcp 3.1.4) — deployed by the installer to `~/.remy-cc/bin/`. Claude Code communicates with it over JSON-RPC to query symbol definitions, call graphs, and impact analysis without subprocess overhead.

The Python server (`index_mcp_server.py`, FastMCP) is retained in-repo as the development-time rendering oracle for the H.4 differential suite (`tests/test_mcp_rust_parity.py`); it is no longer deployed.

## Prerequisites

| Requirement | Notes |
| :--- | :--- |
| `remy-cc` binary | Deployed to `~/.remy-cc/bin/` by `install.py` |
| `logic_index.db` | Generated by `/remy-index` or `struct_scan.py` |

If `REMY_MCP_SERVER_ENABLED=false`, the server prints a note to stderr and exits with code 0.

## Architecture

```
┌─────────────────────┐       JSON-RPC (stdio)       ┌──────────────────────────┐
│   Claude Code       │ ◄──────────────────────────► │  remy-cc mcp         │
│   (MCP client)      │                              │  (rmcp, per-session)     │
└─────────────────────┘                              │  ├─ init_freshness()     │
                                                     │  ├─ 13 tool handlers     │
                                                     │  └─ with_freshness()     │
                                                     └──────────┬───────────────┘
                                                                │ mod
                                                     ┌──────────▼───────────────┐
                                                     │  domain modules          │
                                                     │  ├─ config / common      │
                                                     │  ├─ facts / graph        │
                                                     │  ├─ search / navigate    │
                                                     │  └─ deps / freshness     │
                                                     └──────────┬───────────────┘
                                                                │ rusqlite (WAL)
                                                     ┌──────────▼───────────────┐
                                                     │  .claude/logic_index.db  │
                                                     │  (SQLite, WAL mode)      │
                                                     └──────────────────────────┘
```

**Data flow**: the Rust `remy-cc scan` scanner (Python `struct_scan.py` remains a development-period tool for the oracle and tests) writes symbols, edges, and patterns into `logic_index.db` under the project scan lock. The MCP server opens short-lived read connections (WAL + `busy_timeout=3000`, no write path — INV-R2) per query; MCP reads remain concurrent with the active writer. Query semantics were migrated from the Python owner modules byte-for-byte (H.4 baseline, `docs/MCP_RUST_PARITY_BASELINE.md`).

## Startup & Registration

The server is registered in `~/.claude.json` during installation (template: `remy_mcp.json`):

```json
{
  "mcpServers": {
    "remy-index": {
      "type": "stdio",
      "command": "~/.remy-cc/bin/remy-cc",
      "args": ["mcp"]
    }
  }
}
```

- Claude Code launches the server automatically at session start.
- The server runs for the lifetime of the Claude Code session (one process per session).

### Startup Sequence

1. **`config::load()`**: reads `remy-config.json` (user level, then project overrides) and `REMY_*` process environment; diagnostics for invalid values go to stderr.
2. Environment check: if `REMY_MCP_SERVER_ENABLED=false`, print a stderr note and exit 0.
3. **`init_freshness()`**: probes index staleness (git commit comparison or hash sampling) once, before the tokio runtime starts; the resulting warning string is immutable afterwards.
4. **`serve(stdio())`**: starts the tokio runtime and begins accepting JSON-RPC requests.

### query_impact

Analyze the impact radius of modifying one or more files. Shows both upstream callers and downstream callees of all symbols defined in the target files.

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `files` | `list[str]` | (required) | File paths (forward slashes, relative to project root) |
| `depth_up` | `int` | `3` | Upstream BFS depth |
| `depth_down` | `int` | `3` | Downstream BFS depth |
| `include_ambiguous` | `bool` | `False` | Include ambiguous edges |
| `static_only` | `bool` | `False` | Exclude synthesized edges |

**Output example:**
```
impact analysis for: src/parser.py

upstream (callers into these files):
  [depth 1] 4 file(s), 7 symbol(s): src/loader.py, src/cli.py, src/app.py, tests/test_loader.py
  [depth 2] 6 file(s), 9 symbol(s): src/app.py, src/server.py, src/worker.py, tests/test_cli.py, tests/test_app.py ... +1 more file(s)

### query_search

Search symbols through a deterministic candidate union: an exact-name channel,
a token-prefix channel, and a BM25 summary channel run independently, merge by
node identity, and keep every matching source with its per-source rank. The
edit-distance fuzzy fallback runs only when all three deterministic channels
are empty. Invalid input or a channel execution failure returns an `Error:`
result and does not continue to later channels.

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `text` | `str` | (required) | Query text; operators and punctuation are treated as separators |
| `limit` | `int` | `10` | Result limit in the range `1..REMY_MCP_RESULT_LIMIT` |
| `file_hint` | `str` | `""` | Compatibility alias for `path_hint` |
| `match` | `str` | `"all"` | `all`, `any`, or exact contiguous `phrase` semantics |
| `language` | `str` | `""` | `python`, `c_cpp`, `typescript`, or `rust` parser family |
| `symbol_type` | `str` | `""` | Exact symbol type filter |
| `path_hint` | `str` | `""` | Case-insensitive literal path substring filter |

`file_hint` and `path_hint` may both be supplied only when they normalize to the
same value. Path separators are normalized. `%` and `_` are literal characters,
not wildcards. The location line for symbol type, file, name, and line remains
unchanged; each result adds indented `sources` / `priority` and optional
`sig` / `summary` lines. The exact channel compares the whole query text with
Unicode casefolding and ignores `match`.

**Output example:**
```
search results for 'parse_file' (2 results, matched via union)

  [function] src/parser.py::parse_file  src/parser.py:L42 (Core)
        sources: exact#1, prefix#1 | priority=0
        sig: (path) | summary: parses one source file
  [method] src/loader.py::Loader.parse_file  src/loader.py:L120 (IO)
        sources: prefix#2 | priority=1
```

### query_flow

Find call paths among two or more named symbols via bidirectional BFS.

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `symbols` | `list[str]` | (required, min 2) | Symbol names in traversal order |
| `max_depth` | `int` | `15` | Max BFS depth per pair |
| `max_visited` | `int` | `2000` | Max nodes visited per pair (prevents combinatorial explosion) |
| `static_only` | `bool` | `False` | Exclude synthesized edges |

**Symbol syntax:**
- Bare name: `parse_file`
- Qualified: `src/parser.py::parse_file`
- Class.method: `Loader.parse_file`
- File hint: `parser.py:parse_file`

**Output example:**
```
## Flow (call path among queried symbols)

1. main (src/cli.py:10)
   ↓ call
2. load (src/loader.py:30)
   ↓ call
3. parse_file (src/parser.py:42)
   ↓ call
4. tokenize (src/tokenizer.py:15)
```

1. main (src/cli.py:10)
   ↓ call
2. parse_file (src/parser.py:42)

[Break: pair (parse_file, unrelated_func) not connected within depth=15]

3. unrelated_func (src/other.py:5)
```

### query_navigate

Locate work by natural-language intent over bounded cluster/file/symbol
candidates. The intent is tokenized and run through the P1.3 deterministic
channels with `any` semantics: symbol candidates come from the
exact/prefix/BM25 union (single-word intents additionally try the fuzzy
channel when all deterministic channels are empty), and file/cluster
candidates come from a BM25 query over the projection rows (name, path
tokens, path, and summary columns, weighted). Each layer is capped by its
quota parameter; only the selected candidates are read and sent to the LLM.
Symbol candidates carry their file and cluster, and file candidates carry
their cluster, so every result supports layer-by-layer drill-down.

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `intent` | `str` | (required) | Natural-language intent; English is recommended because index summaries are stored in English |
| `top_k` | `int` | `5` | Result cap, clamped to `1..20` |

The header `source=` label reports the path taken: `llm` (candidate prompt
ranked by the LLM), `llm-cluster-only` (lexical candidates empty — e.g.
non-English intents — so all cluster summaries were ranked instead),
`heuristic` (no LLM configured; deterministic candidate order),
`heuristic-fallback` (LLM response unparseable), or `cache`. Rankings are
cached in `judge_cache` under a key derived from the normalized intent,
`top_k`, the candidate `(node_ref, content_hash)` sequence, and the prompt
template version — summary writes unrelated to the candidates do not
invalidate the cache.

**Output example:**
```
## Navigate results for 'locate authentication token parser' (top 2, source=llm)

1. [0.92] security / auth/token_parser.py :: parse_token
   - parses and validates raw tokens
2. [0.55] security / auth/session.py
   - session lifecycle around token use
```

### query_dependencies

Analyze file-level import/include relations — the pure import dependencies the
call graph does not express. The dependency graph merges the stored resolved
imports (`files.imports`) with query-time unique-suffix derivation from
`files.import_bindings` (the same `derive_import_bindings` rule the scanner's
edge resolution uses, so scan-time and query-time semantics cannot drift).
Multi-hit bindings produce no edge (unique-only); stdlib modules are
short-circuited. Entries stored in `imports` that are not present in the
files table are rendered with a `(not indexed)` marker.

| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `files` | `list[str]` | (required) | Project-relative paths; backslashes are normalized |
| `direction` | `str` | `both` | `up` = files importing the targets, `down` = files the targets import, `both` = both sections |
| `depth` | `int` | `2` | BFS depth, clamped to `REMY_MCP_BFS_MAX_DEPTH` |

Levels are lexicographically sorted; each file appears only in its
first-reached level (cycles terminate via the visited set).

**Output example:**
```
dependency analysis for: app/main.py

imported by (upstream importers):
  (none)

imports (downstream dependencies):
  [depth 1] 2 file(s): app/util.py, libs/helpers.py
  [depth 2] 1 file(s): vendor/missing.py (not indexed)

summary: 0 upstream file(s), 3 downstream file(s)
```

**Errors:**
- Invalid direction: `Error: direction must be one of up/down/both.`
- No target in the index: `No indexed files found matching: <inputs>`

This tool is Rust single-implementation (no Python oracle arm); its acceptance
surface is `tests/test_mcp_dependencies.py`, not the H.4 differential matrix
(see `docs/MCP_RUST_PARITY_BASELINE.md` §4.2).

## Configuration

All Python runtime parameters are stored in `~/.claude/remy-config.json` with
optional project overrides in `<project>/.claude/remy-config.json`. The
`remy-cc config` UI edits these files. Same-named `REMY_*` process environment
variables override file values for that process tree.

| Variable | Default | Description |
| :--- | :--- | :--- |
| `REMY_MCP_SERVER_ENABLED` | `true` | Disable the MCP server on its next launch |
| `REMY_MCP_BFS_MAX_DEPTH` | `5` | Hard cap on BFS depth for callers/callees/impact/dependencies |
| `REMY_MCP_RESULT_LIMIT` | `50` | Shared result cap for BFS levels and query_search |
| `REMY_MCP_STATIC_ONLY_DEFAULT` | `false` | Internal default when a query implementation receives `static_only=None`; public MCP tools retain `false` |
| `REMY_FLOW_MAX_DEPTH` | `15` | Hard cap on query_flow depth |
| `REMY_FLOW_MAX_VISITED` | `2000` | Hard cap on query_flow visited nodes |
| `REMY_NAVIGATE_CANDIDATE_CLUSTERS` | `5` | Cluster candidate cap per query_navigate intent |
| `REMY_NAVIGATE_CANDIDATE_FILES` | `10` | File candidate cap per query_navigate intent |
| `REMY_NAVIGATE_CANDIDATE_SYMBOLS` | `10` | Symbol candidate cap per query_navigate intent |
| `REMY_LOGIC_INDEX_DB_PATH` | `.claude/logic_index.db` | Database path relative to the project root |

## Index Staleness Detection

On startup, `init_freshness()` (`remy-cc/src/mcp/freshness.rs`) checks whether the index is current:

```
┌─────────────────────────────┐
│ Read source_commit from DB  │
└──────────┬──────────────────┘
           │
     ┌─────▼─────┐     yes    ┌──────────────────┐
     │ git avail?├────────────│ Compare HEAD vs  │
     └─────┬─────┘            │ source_commit    │
           │ no               └────────┬─────────┘
           │                           │
           │                     ┌─────▼──────┐
  ┌────────▼───────────┐         │  Match?    │
  │ Hash sampling      │         └──┬──────┬──┘
  │ (10% of files,     │         yes│      │no
  │  max 10 samples)   │            │      ▼
  └────────┬───────────┘            │  ┌──────────────────────┐
           │                        │  │ Warning: commit drift│
           │                        │  └──────────────────────┘
  ┌────────▼───────────┐            │
  │ >20% differ?       │   ┌────────▼─────────────┐
  │ >50% differ?       │   │ Check git status     │
  └────────────────────┘   │ (porcelain)          │
                           └────────┬─────────────┘
                                    │
                              ┌─────▼──────┐
                              │ >20% dirty?│──► Warning
                              └────────────┘
```

When a warning is generated, it is prepended to every tool response:

```
[Warning: index built at commit a1b2c3d4, current HEAD is e5f6g7h8. Run /remy-index to rebuild.]

symbols matching 'parse_file' (1 results)
  ...
```

The warning does NOT block tool usage — results are still returned, but may be incomplete or stale.

## MCP Minimal Mode

When the MCP server is running, the context injection system (`injector.py`) switches from injecting the full logic tree (~40 KB of symbol signatures and summaries) to a minimal payload (~1 KB):
- Cluster overview table (cluster name, file count, entry files)
- MCP tool usage hints (when to use which tool)

This reduces the baseline context consumption while maintaining full query capability on demand.

## Troubleshooting

### "Error: logic_index.db not found"

The database does not exist at the expected path. Run `/remy-index` to generate it, or verify `REMY_LOGIC_INDEX_DB_PATH` points to the correct location.

### Stale results after code changes

The index is built from a snapshot. If you modify source files after the last scan:
1. The staleness warning will appear (if >20% files differ).
2. Run `/remy-index` to rebuild, or wait for the next SessionStart auto-scan.

### MCP server not starting

Check:
1. `~/.remy-cc/bin/remy-cc --version` runs and reports the deployed version
2. `~/.claude.json` contains the `remy-index` entry under `mcpServers` (command = the daemon binary, args `["mcp"]`)
3. `REMY_MCP_SERVER_ENABLED` is not set to `false`

Diagnostic: run manually and check stderr (config diagnostics and the disabled note go there):
```bash
~/.remy-cc/bin/remy-cc mcp
```

### First tool call hangs (historical — Python oracle only)

This failure mode applies only to the development-time Python oracle (`index_mcp_server.py`), not the Rust production host. On Windows, `subprocess.run(capture_output=True)` inside an asyncio tool handler deadlocks: the ProactorEventLoop's I/O completion ports conflict with pipes created in the same process, so the subprocess read never completes. The fix (v1.4.3) moved all subprocess calls into the oracle's `_init_freshness()`, before `mcp.run()` starts the event loop. When modifying the oracle, keep `subprocess.run` / `subprocess.Popen` / `os.popen` out of every tool handler code path.

### Architectural Constraints (Rust host)

**INV-1**: External process invocations (git probes) happen only inside `init_freshness()`, which runs before the tokio runtime starts (`mod.rs::run` ordering). Tool handler code paths spawn no processes; the navigate LLM call uses in-process `reqwest`.

**INV-2**: The freshness warning is computed once by `init_freshness()` and shared read-only (`Arc<String>`); tool handlers never mutate it.

**INV-3**: `with_freshness(result)` skips the warning prefix when the result starts with `Error:` — error messages are returned as-is (`common.rs`).

**INV-4**: Each query opens a short-lived rusqlite connection (WAL + `busy_timeout=3000`) and never writes — the read path stays out of the daemon write topology (INV-R2).

Historical oracle constraint: the Python FastMCP oracle additionally forbids subprocess calls in tool handlers (Windows ProactorEventLoop deadlock — see Troubleshooting).

### Adding a New Tool

1. Implement `query_xxx_impl(...)` in the domain module owning the concern under `remy-cc/src/mcp/` (create a new module for a new domain, e.g. `deps.rs`).
2. Register in `mod.rs`: a `Params` struct (serde defaults + schemars) + a `#[tool]` method wrapping the impl in `self.wrap(...)` + one INSTRUCTIONS line.
3. Decide the verification surface per `docs/MCP_RUST_PARITY_BASELINE.md` §4.2: a tool with a Python oracle arm joins the differential matrix; a Rust single-implementation tool gets a dedicated suite (see `tests/test_mcp_dependencies.py`) and an entry in the parity `RUST_ONLY_TOOLS` allowlist.
4. Permission is already covered by the `mcp__remy-index__*` wildcard in `settings.example.json`.
5. Sync the registration surface: this README (+ `_zh`), the project READMEs, the workspace `CLAUDE.md` tool count, `hooks/doc_manager/mcp_minimal_template.json`, and `docs/TESTING.md` (+ `_zh`).

### Edge Confidence Tiers

The `edges` table has a `provenance` column with 4 confidence levels:

| Level | Meaning | `static_only=True` |
| :--- | :--- | :--- |
| `definite` | Direct AST-resolved call | Included |
| `probable` | Name-matched cross-file call | Included |
| `inferred` | Synthesized via interface dispatch, observer pattern, or signal connection | **Excluded** |
| `speculative` | Ambiguous resolution candidate (multiple targets) | **Excluded** |

When `static_only=True`, only `definite` and `probable` edges are traversed. This produces tighter, more reliable results at the cost of missing polymorphic dispatch paths.
